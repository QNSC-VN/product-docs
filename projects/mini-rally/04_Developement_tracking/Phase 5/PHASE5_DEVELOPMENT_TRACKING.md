## 2. Why Portfolio, and the concepts behind it

Mini Rally's Backlog today only knows two Work Item types: **Story** and **Defect** (with **Task** as their child). Portfolio adds hierarchy **above** Story/Defect so leadership can see and plan work at larger outcome/capability levels instead of one Story at a time. This is modeled on Rally's **Portfolio Item hierarchy**, simplified to **2 levels** for Mini Rally's scale:

```
Epic                         (Project-level grouping of Features)
   |
Feature                      (lowest Portfolio Item; attaches to Story/Defect)
   |
   Story / Defect            (already exists - Backlog, Phase 1)
        |
        Task                  (already exists - Phase 2)
```

- **Epic** - a Project-level grouping of multiple Features. Mini Rally labels Rally's `Initiative`-like level as Epic. Epic has no Team field and rolls up leaf Story/Defect through its child Features.
- **Feature** - one large, shippable capability (example: "Advanced Reporting Module"). A Feature is the lowest Portfolio Item level in Mini Rally and links directly to Story/Defect - this mirrors Rally's rule that only the lowest Portfolio Item type attaches to the User Story hierarchy. A Feature's progress is a rollup of its child Stories/Defects (not a manually typed number).
- Everything below Feature (Story, Defect, Task) already exists and stays on the shared Work Item/Task templates. The 2026-07-26 P5.1 amendment explicitly aligns those shared templates with Portfolio membership, Backlog/Iteration visibility and Task hour rules; it does not create a separate Portfolio-only Work Item or Task flow.
- **2026-07-28 Epic amendment:** BA re-promoted the Rally `Initiative` concept under the Mini Rally name **Epic**. Scope is intentionally narrow: Epic is Project-level, uses the Feature template/flow, owns its own Preliminary/Refined estimates, and aggregates child Features. Theme/deeper Portfolio hierarchy remains out of scope.

## 5. Status Legend

Feature delivery uses one consistent flow:

`PROPOSED -> BA CONFIRMED -> DOCS ALIGNED -> MOCKUP IMPLEMENTED -> VERIFIED -> BA ACCEPTED -> FEATURE CLOSED`

`BA/Mockup readiness` and `Production implementation readiness` are tracked separately. A feature can be BA accepted while production remains `NOT STARTED`.

For every product feature:

1. Propose objective, in/out scope, decisions, tasks and acceptance criteria.
2. Wait for explicit BA confirmation; make no feature edit before this gate.
3. Align SRS, tracker, workbook and decision log.
4. Implement the confirmed mockup/code slice.
5. Build and browser-smoke-test.
6. Update test scenarios, traceability and evidence.
7. Obtain BA acceptance, then close the feature and move to the next one.
